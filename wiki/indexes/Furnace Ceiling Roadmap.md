# 炼丹炉上限路线图

这份文档回答的是：

- 炼丹炉现在已经做到哪一步
- 从现在到真正上限，还差哪些阶段
- 每个阶段要解决什么问题
- 哪些东西暂时不该做

它不是替代 [[wiki/indexes/Alchemy Furnace|炼丹炉架构]] 的主文档，而是主文档的后续演化路线。

如果你要看“真正做成后，它最终会长成什么样”，再读：

- [[wiki/indexes/Furnace Ultimate Architecture|炼丹炉最终极形态]]

## 当前所在位置

当前炼丹炉已经具备：

- `raw / wiki / machine memory / schema / outputs` 五层主线
- `review / aging / escalation / repair / nightly` 治理闭环
- `decision / judgment` 判断沉淀层
- `general / investing / research / product / ops` 多协议运行时
- `dry-run / bundle / apply / receipt / revert / audit` 执行层
- `furnace-center / review-center / execution-center / graph-view` 基础产品壳

所以它已经不是“原型想法”，而是一个可长期使用的 local-first 知识操作系统 V1。

但它距离真正上限，还差的不是更多入口，而是更硬的知识层、更值钱的判断层、更稳的执行治理，以及真实高密度场景压测。

## 上限定义

炼丹炉的上限不是“更会做笔记”，而是：

**把高质量原料持续炼成可追溯、可复审、可执行、可复利的判断资产。**

达到上限时，系统应该像这样工作：

- 概念层足够硬，能承受长期重写、冲突和领域迁移
- 判断层足够值钱，能稳定沉淀 thesis、tradeoff、决策 memo 和失效条件
- 执行层足够稳，能安全处理低风险修复并留下完整审计链
- 产品壳足够顺手，人每天只在一个工作台里投料、查询、审阅和处理动作
- 协议层足够成熟，能在一个统一炉子里支撑投资、研发、产品、运营等高价值场景

## 阶段 1：硬化概念层

目标：

- 让 `wiki/concepts/` 从“有页面”升级成“硬概念库”

需要补强的能力：

- 更稳定的冲突显式化
- 更明确的证据缺口和反证区块
- 更稳的 merge / split 建议
- 更强的弱概念页重写优先级
- 概念页对 `judgment / decision` 的直接支撑

完成标准：

- 高价值概念页不再只是摘要拼接
- 概念冲突、证据缺口和失效条件能被显式跟踪
- `concept-quality` 不只是看板，而是概念维护工作台

非目标：

- 不做全自动大规模概念页重写
- 不跳过 review 直接改写高价值概念层

## 阶段 2：资产化判断层

目标：

- 让 `decision / judgment` 从“可记录”升级成“可复利资产”

需要补强的能力：

- 更强的模板化结构
- 更硬的 `citations / confidence / invalidation / revisit_after`
- 更明确的 recurring promotion 规则
- 更稳的协议化判断模板
- 更清晰的判断演化历史

完成标准：

- 判断页天然带证据、反证、置信度、复审与失效条件
- 判断可以被复审、推翻、升级，而不是只做一次性结论
- 高价值输出可以稳定沉到 `decision / judgment`

非目标：

- 不把系统变成自动投资决策机或自动架构裁决机
- 不跳过人工判断权

## 阶段 3：治理化执行层

目标：

- 让执行层从“可操作”升级成“可信赖治理层”

需要补强的能力：

- 更细的 `execution_band`
- 更强的 page-level patch plan
- 更清晰的 apply policy stratification
- 更稳的 receipt / revert / audit / consistency guard
- 执行动作与 review / protocol / machine memory 的闭环对齐

完成标准：

- 低风险修复可以安全预演、执行、回滚、审计
- 中风险修复有 reviewable patch plan
- 高风险修复明确停在人工边界外

非目标：

- 不自动执行高风险 repair
- 不跨越 `raw` 事实层做静默覆盖

## 阶段 4：产品化控制面板

目标：

- 让产品壳从“多个入口页”升级成“统一工作台”

需要补强的能力：

- 把 `furnace-center / review-center / execution-center / graph-view` 更强地统一
- 更直接地显示今日焦点、协议焦点、review 焦点和 execution 焦点
- 更清晰的人机边界
- 更好的图谱可视化与执行审计浏览体验

完成标准：

- 用户每天主要只在一个工作台里完成大部分操作
- 审阅、修复、图谱、输出、回执和协议状态可从统一入口进入
- 入口不再分散成“看板集合”

非目标：

- 不强行转成 hosted SaaS
- 不为了 UI 统一而破坏 file-based local-first runtime

## 阶段 5：高密度场景压实

目标：

- 用真实高价值场景证明“知识复利”真的发生

推荐优先场景：

- `investing`
- `research`
- `product`
- `ops`

做法：

- 用真实、连续、高密度原料跑几个月
- 观察概念层是否越来越硬
- 观察判断层是否越来越值钱
- 观察 execution / review / repair 是否真的省脑力
- 观察跨协议迁移是否带来复利

完成标准：

- 系统不只是“功能很多”，而是明显降低重复判断成本
- 旧判断会被自动拉回复审
- 新问题会更快落到已沉淀知识上
- 用户愿意长期使用而不是回退到普通笔记库

非目标：

- 不追求短期 demo 效果
- 不用轻量随记场景证明系统上限

## 不该优先做的事

以下内容不是当前上限路线的主矛盾：

- 再接更多模型后端
- 再加更多投料入口
- 再造一套新的炉子
- 过早做 hosted SaaS
- 引入重型向量库或 fine-tuning 作为第一优先级

这些都可能有价值，但现在更重要的是：

- 概念更硬
- 判断更值钱
- 执行更稳
- 工作台更顺手
- 真实场景更密

## 推荐执行顺序

1. 硬化概念层
2. 资产化判断层
3. 治理化执行层
4. 产品化控制面板
5. 高密度场景压实

这 5 步不是完全串行，但依赖关系很明确：

- 没有硬概念层，判断层容易漂
- 没有判断层资产化，系统很难产生真正复利
- 没有治理化执行层，系统只能“会建议”
- 没有统一工作台，采用成本会偏高
- 没有真实高密度场景，所有上限都只是纸面上限

## 一句话总结

炼丹炉现在已经是一套强 V1；  
从现在到上限，不是继续堆功能，而是：

**把知识层变硬，把判断层变值钱，把执行层变可靠，再用真实高密度场景把整个系统压实。**
